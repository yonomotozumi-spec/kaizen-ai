# Kaizen AI コーポレートサイト

`website/` は会社の顔であり、営業の道具でもある。読者は**従業員10〜300名の中小企業、士業・不動産・建設・医療・教育の決裁層**で、多くは非IT・50〜60代。この読者像が、以降のほぼ全ての判断の理由になっている。

## 最初に読む場所

| やること | 読むもの |
|---|---|
| 色・書体・レイアウトを触る | `references/design-system.md` |
| 事例・実績を載せる／数値を書く | `references/case-studies.md` ← **誇大表示の防止線がここにある** |
| 何か壊れた・壊しそう | `references/pitfalls.md` ← 実際に踏んだ罠の一覧 |

## ファイル構成

```
website/
├── index.html          トップ（1枚もののLP）
├── cases.html          改善例（実例＋想定モデルケース、#アンカーで個別リンク）
└── assets/style.css    全ページ共通
```

外部ライブラリ・外部フォント・外部画像は**一つも使っていない**。CDNを足そうとしないこと。図もグラフもアイコンも全てインラインSVGで、これは Artifact のCSPが外部ホストを遮断することと、日本語Webフォントが数MBになることの両方への答えになっている。

## 変更の手順

1. **`assets/style.css` を直す。** 各ページの `<style>` ではない。2ページが共有している。
2. **暗地の定義には手を入れない。** 明地の見た目を直すときは `.bg-washi` / `.bg-paper` 配下の上書きを足す。加算方式にしてあるので、セクションのクラスを付け替えるだけで暗⇔明を戻せる。
3. **色を足したら `scripts/contrast.mjs` を通す。**
4. **`scripts/check.mjs` を通す。** 画面2種＋印刷を実際に描画して、JSエラー・横スクロール・印刷の落ち残りを拾う。
5. **スクリーンショットを見る。** 検証スクリプトは「壊れていない」しか言わない。レイアウトの良し悪しは目で見るしかない。

```bash
node .claude/skills/kaizen-website/scripts/contrast.mjs
node .claude/skills/kaizen-website/scripts/check.mjs --shots /tmp/shots
```

## セクションの地色 —「暗は印象、明は情報」

| 暗（藍） | 明（紙白） |
|---|---|
| ヒーロー、ミッション、行動指針の帯、アプローチ、最終CTA、フッター | 課題、サービス、改善例、料金、選ばれる理由、流れ、FAQ、改善例ページ本文 |

全編ダークも試したが戻した。コントラスト基準自体は満たしていた（本文15:1）ので「読めない」わけではない。戻した理由は数字に出ない側にある — 決裁層の年齢、明るいオフィスでの閲覧、紙に出す運用、そして**全編ダークは「Web系スタートアップ」の記号**で、発注して安心な相手には見えにくいこと。

**迫力は捨てていない。** ヒーローの巨大な「改善」も縦書きのミッションも残っている。暗さを効かせる場所を絞っただけ。新しくセクションを足すときは、**読ませるものか、印象を作るものか**で地色を決める。明地の中は `--washi`（#F2F5FA）と `--paper`（#FFFFFF）を交互に敷いてリズムを作る。

## 絶対に外してはいけないもの

**朱は用途で2値。** `--shu` (#E8543F) は文字・罫・図の強調用、`--shu-btn` (#C23D29) は面を塗る用。`--shu` でボタンを塗ると白文字が 3.64 になり基準4.5を割る（一度やった）。面には必ず `--shu-btn`。

**グラフの色はブランド色そのままでは使えない。** `#22335C` は明度が、`#C6A868` は彩度が、データ可視化の基準（OKLCH L 0.43–0.77 / C ≥ 0.10）を外れる。色相を保って基準内に上げた `#345BA8`（自動・肯定側）と `#BE9433`（人が確認・中立側）が検証済みの値。新しい色を足すなら `dataviz` スキルの `scripts/validate_palette.js` を必ず通す。

**1pxグリッドはセルの `box-shadow` で引く。** コンテナ背景を罫色にする方式は、要素数が列数の倍数でないとき空セルが色の塊になって出る（目次7件・サービス8件で実際に出た）。

**絵文字は使わない。** アイコンは `<symbol>` 定義 + `<use>`。環境で字形が変わるし、素人っぽく見える。

**固有名詞に `text-transform: uppercase` をかけない。** 顧客名 `kikitori` が `KIKITORI` になっていたことがある。

## 事例を載せるとき

**Kaizen AI は2026年設立で、公開できる実績が少ない。** だからこそ、実例と想定モデルケースの線引きは飾りではなく会社の信用そのものになる。

- 実例には**実測値しか書かない**。時間削減の数字が無いなら、無いまま出す。項目数や法令数のような**数えられる事実**は書ける
- 想定ケースには「想定ケース」バッジと注意書きを、**グラフや数値と同時に視界に入る位置**に置く。グラフは数字を実際以上に権威づけるので、離すと誤読される
- **顧客名を出すには先方の掲載許可が要る。** 業種と規模だけでも特定されうる
- 情報が足りないまま埋めない。補って書いた箇所があるなら `website/README.md` に書き残し、ユーザーに伝える

詳しい書式と、効果の表に「測り方」の列を置く理由は `references/case-studies.md`。

## Artifact でプレビューを出す

外部ファイルを読めないので、CSSをインライン化した単一ファイルを作ってから publish する。

```bash
# 相手側を先に publish して URL を取り、それを置換に渡す
node .claude/skills/kaizen-website/scripts/build-artifact.mjs \
  cases.html "改善例 — Kaizen AI" \
  "index.html=<トップのArtifact URL>" --out /tmp/cases-artifact.html
```

同じファイルパスで再 publish すればURLは変わらない。ページごとにパスを分けること（パスを変えると別のArtifactになる）。

## 本番公開について

Artifact は claude.ai 上のプレビューであって、**独自ドメインの本番HPにはならない**。本番は Vercel / Netlify 連携を想定（`website/README.md` に記載）。このリポジトリは顧客情報を含むため Public 化は非推奨。

## 触る前に確認すること

**お問い合わせ先がまだ「準備中」のまま。** LPとして最大の未完部分で、ここが埋まって初めて機能する。メールアドレスかフォームが確定したか、作業のたびに確認する価値がある。
