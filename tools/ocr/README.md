# 紙の書類 → データ化ツール（OCR / 帳票読み取り）

**生成AI（LLM）を一切使いません。したがってAPIトークンの消費はゼロ、従量課金も発生しません。**
すべてローカルで処理するため、書類が外部に送信されることもありません（顧客の機密書類を扱う前提で設計）。

| | |
|---|---|
| 何をするか | 請求書・領収書・納品書をスキャン画像/PDFから読み取り、項目をCSVに落とす |
| 使うもの | Tesseract OCR（オープンソース）＋ OpenCV による前処理 ＋ 正規表現 |
| かかるお金 | **0円**（ソフトはすべて無償・オフライン動作） |
| 得意 | 活字の定型帳票（請求書・領収書・納品書・注文書） |
| 苦手 | 手書き、レイアウトが毎回変わる書類、極端な低解像度 |
| 実測 | **200dpi以上のスキャンで項目正解率 84〜95%**。100dpi以下は実質不可（[詳細](#実測した精度)） |

---

## セットアップ

```bash
# 1. OCRエンジンと日本語データ（Ubuntu / Debian）
sudo apt install tesseract-ocr tesseract-ocr-jpn tesseract-ocr-jpn-vert poppler-utils

# 2. Python側
pip install -r requirements.txt
```

macOS の場合は `brew install tesseract tesseract-lang poppler`。
Windows は [UB Mannheim版インストーラ](https://github.com/UB-Mannheim/tesseract/wiki) で日本語データを選択。

インストール確認:

```bash
tesseract --list-langs     # jpn / jpn_vert が出ればOK
python3 test_ocr.py        # 33件すべてOKになればOK
```

## 使い方

```bash
# 1ファイルを読む
python3 ocr.py samples/請求書サンプル_スキャン.jpg

# フォルダを一括処理してCSVに（実務はこれがメイン）
python3 ocr.py scans/ -o 結果.csv --items 明細.csv

# 帳票の種類を明示する（既定は本文から自動判定）
python3 ocr.py 領収書.jpg --type receipt

# 認識テキストだけ欲しいとき
python3 ocr.py 契約書.pdf --text-only

# JSONで他システムに渡す
python3 ocr.py scans/ --json > 結果.json
```

主なオプション:

| オプション | 用途 |
|---|---|
| `--type {auto,invoice,receipt,delivery}` | 帳票テンプレートの指定（既定 `auto`） |
| `--lang jpn+eng` | 英日混在の書類 |
| `--dpi 400` | PDFの画像化解像度を上げる（精度↑・速度↓） |
| `--keep-rules` | 罫線を除去しない（表のない書類向け） |
| `--force-ocr` | テキスト層のあるPDFでも強制的にOCR |
| `--psm 4` | 段組みが崩れるときにページ分割モードを変える |
| `--save-text out/` | 認識テキストをファイルに保存 |

## 処理の流れ

```
入力（PDF / JPG / PNG / TIFF）
  │
  ├─ PDFにテキスト層あり ─→ そのまま抽出（OCRしない＝誤認識ゼロ・一瞬）
  │
  └─ 画像 / スキャンPDF
        ↓ 拡大（幅1800px未満なら）
        ↓ 傾き補正（±5°まで）
        ↓ 二値化
        ↓ 罫線除去          ← ここが精度の分かれ目
        ↓ Tesseract OCR（日本語）
        ↓ 誤認識の規則補正
        ↓ 正規表現で項目抽出
        ↓ 検算
      CSV / JSON / テキスト
```

**罫線除去がなぜ重要か。** 表の罫線が残っているとTesseractがセルの枠を文字として扱い、
表の中身がほぼ全滅します。実測では、罫線を消さずにOCRした場合の明細行は次の通りでした。

```
（罫線あり）  CT / 革つ| / NN / 区RSSI     ← 判読不能
（罫線除去後） 業務診断 (アセスメント) | 1 | 450,000 | 450,000   ← 正しく取れる
```

## 誤認識への対策

### 1. 規則による自動補正

実測で頻出したパターンだけを、意味を推測せずに機械的に直します。

| 誤認識 | 補正後 | 理由 |
|---|---|---|
| `1.350,000` | `1,350,000` | 桁区切りのカンマがピリオドに化ける |
| `\33 0,000` | `\330,000` | 通貨記号のあとの数値に空白が入り込む |
| `11234567890123` | `T1234567890123` | インボイス登録番号の先頭Tが1に化ける |
| `Alワークフロー` | `AIワークフロー` | 大文字I と 小文字l の取り違え |
| `令和8年7月15日` | `2026-07-15` | 和暦の西暦変換 |

### 2. 検算による誤読の検出

**OCRで本当に怖いのは未検出ではなく「もっともらしい誤読」です。**
未検出は `（要確認）` と出るので気づけますが、`800,000` が `809,000` と読まれた場合、
出力を見ただけでは誰も気づけません。

そこで帳票が本来持っている冗長性を使って機械的に炙り出します。

- 小計 ＋ 消費税 ＝ 合計金額 か
- 明細行の金額合計 ＝ 小計 か
- 消費税率が 8% / 10% の範囲に収まっているか
- 支払期限が発行日より後か
- 登録番号が「T + 13桁」の形式か

引っかかると `⚠ 検算NG` として出力され、CSVの先頭列に `要確認` が立ちます。

### 3. 推測で埋めない

読み取れなかった項目は `（要確認）` と明示します。
もっともらしい値で埋めることはしません（`gijiroku.py` / `teiansho.py` と同じ方針）。

## 実測した精度

**書式6種 × 画質5段階 = 30通り**で計測しました。書式はフォント（ゴシック／明朝／等幅）、
レイアウト、言い回し（「ご請求金額」「御請求金額」、「お支払期限」「お支払期日」）、
罫線の有無、和暦／西暦をそれぞれ変えてあります。採点対象は190項目。

### 画質で決まる（ここが最大の要因）

| 画質 | 正解率 | 誤り率 | 平均信頼度 | 無修正で通過した書類 |
|---|---|---|---|---|
| 300dpi相当 | 92.1% | 0.0% | 89.3 | 4/6件 |
| 200dpi相当 | 94.7% | 2.6% | 87.0 | 4/6件 |
| 150dpi相当 | 84.2% | 0.0% | 83.9 | 1/6件 |
| 100dpi相当 | **5.3%** | 2.6% | 39.4 | 0/6件 |
| 75dpi相当 | **0.0%** | 2.6% | 25.9 | 0/6件 |

**150dpiと100dpiの間に断崖があります。** なだらかに悪化するのではなく、
ある点を境に一気に壊れます。スキャン設定が実質的にすべてを決めます。

PDFにテキスト層がある場合（電子請求書をPDFのまま受け取った場合）はOCRを通らないため、
**正解率100%・誤りゼロ**です。ここが最も確実な経路になります。

### OCR信頼度が実用可否の指標になる

30件を信頼度で層別すると、はっきり分かれます。

| OCR信頼度 | 件数 | 正解率 | 誤り率 | 無修正で通過 |
|---|---|---|---|---|
| 85以上 | 13 | 94.1% | **0.0%** | 9/13件 |
| 75〜85 | 5 | 79.3% | 3.4% | 0/5件 |
| 60未満 | 12 | 2.6% | 2.6% | 0/12件 |

**信頼度85以上に限れば、誤って出力された項目はゼロでした。**
自動処理に回すかどうかのしきい値として、そのまま使えます（`--warn-confidence` で調整）。

### 書式別

| 書式 | 正解率（画質5段階の合計） |
|---|---|
| 請求書（罫線なし・スペース区切り） | 57.8% |
| 請求書（ゴシック・罫線あり） | 55.6% |
| 納品書 | 60.0% |
| 領収書（和暦） | 60.0% |
| 請求書（明朝・言い回し違い） | 53.3% |
| レシート（感熱紙風・細字・低コントラスト） | 40.0% |

使える画質（150dpi以上）に限れば書式による差は小さく、**フォントや言い回しが変わっても
ほぼ同じ精度が出ます**。ただし感熱レシートだけは細字・低コントラストのため一段落ちます。

帳票種別の自動判定（請求書／領収書／納品書）は、150dpi以上で **18/18件正解**でした。

### 危険なのは「未検出」ではなく「誤読」

30件・190項目のうち、**誤って出力された項目は3個（1.6%）**でした。
未検出（82個）は `（要確認）` と出るので気づけますが、誤読は出力を見ても気づけません。

実際に出た3件はいずれも**検算をすり抜けました**。

| 書類 | 誤読 | 信頼度 | なぜ検算で捕まらないか |
|---|---|---|---|
| 領収書 | 日付 `2026-07-15` → `2026-07-05` | 81.4 | 日付は他の項目と突き合わせられない |
| 請求書 | 番号 `2026-0842` → `2026-O9432` | 30.5 | 番号は検算のしようがない |
| 領収書 | 金額 `330,000` → `30,000` | 37.9 | 領収書には小計・税の内訳がなく検算できない |

ここから言えることは明確です。

- **請求書は守れる。** 小計＋税＝合計、明細合計＝小計 という冗長性があるため、金額の誤読は検算で捕まる
- **領収書・レシートは守れない。** 金額が1つしかなく、突き合わせる相手がいない
- **日付と番号はどの帳票でも守れない。** 検算の対象にできない

したがって **領収書・レシートの金額と、全帳票の日付・番号は、金額の検算とは別に
目視確認の対象**にしてください。信頼度85未満はそもそも自動処理に流さないのが安全です。

### 分かっている限界

- **手書きは読めません。** Tesseractは活字前提の設計です。
  なお本ベンチマークに手書きフォントが用意できなかったため、**手書きは未計測**です。
  「読めない」は設計上の性質であり、この計測で示した数字ではありません
- **200dpi未満で急激に悪化。** スキャン設定は300dpi・グレースケール推奨
- **印影が数字に重なると、その項目は落ちます**（誤った値を出すのではなく未検出になるので安全側）
- **感熱レシートは一段落ちる**（細字・低コントラスト・退色）
- **書式が想定外だと項目が取れません。** 項目抽出は「ラベル→値」の正規表現なので、
  未知の言い回しには `TEMPLATES` に規則を足す必要があります
- **縦書きは `--lang jpn_vert` が必要**（自動では切り替えません）

### この数字をそのまま顧客に出さないでください

計測に使ったのはHTMLから生成した合成帳票です。実物には、折り目、汚れ、手書きの追記、
複写伝票の裏写り、退色、傾いた押印など、ここで再現できていない要素があります。

**必ず顧客の実物を10〜20枚読ませて、その結果を提示してください。**
そのための計測スクリプトを同梱しています（次節）。

## 自社・顧客の実物で精度を測る（`bench.py`）

```bash
# 1. 正解CSVのテンプレートを作る
python3 bench.py --init 正解.csv

# 2. 実物の帳票をフォルダに集め、正解.csv に正解値を手で書く（1回だけ）
#    空欄の項目は採点しません

# 3. 計測
python3 bench.py scans/ 正解.csv -o 採点結果.csv
```

出力されるもの:

- 正解 / 誤り / 未検出 の件数と率
- **無修正で通過した書類の割合**（運用でいちばん効く指標）
- 誤って出力された値の一覧と、検算で捕まえられたかどうか
- **OCR信頼度ごとの精度**（自動処理に回すしきい値を決める材料）

商談では、この出力をそのまま提示するのが最も誠実で、最も説得力があります。

## 精度を上げるには

1. **スキャン設定を直す（効果が一番大きい）** — 300dpi・グレースケール・傾けない
2. **PDFはテキスト層を残す** — 電子請求書をPDFのまま受け取ればOCRは不要になり、誤認識はゼロになる
3. **`TEMPLATES` に取引先ごとの規則を足す** — `ocr.py` 内の辞書に正規表現を1行足すだけ
4. **それでも足りない場合** — 日本語文書に特化したOSS（YomiToku、PaddleOCR等）や
   クラウドOCR（Google Document AI、Azure Document Intelligence 等）への切り替えを検討する。
   ただしクラウドOCRは**従量課金**であり、書類が外部に送信されます

> 生成AI（LLM）に画像を渡せば項目抽出の精度は上がりますが、
> **トークン課金が発生し、書類が外部に送信されます。**
> 「トークンを使わない」が要件である限り、この構成が現実的な最適解です。

---

## 運用ルール

1. **出力は必ず原本と突合してから使う。** 特に金額・日付・口座番号
2. **会計システムへの取り込み前に、`要確認` 列でフィルタして目視確認する**
3. 顧客の書類を扱う場合は、事前に取り扱い範囲を合意する（`templates/engagement-checklist.md` 参照）
4. 検算を通った項目も誤認識の可能性は残る。検算は「間違いを見つける」もので「正しさを保証する」ものではない
